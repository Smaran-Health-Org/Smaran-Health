# Read-only phone preview assessment

Current Mac preview: `http://smaran-auth-qa.localhost:56731`, bound to `127.0.0.1:56731` (PID 92392). The browser's Supabase URL is `http://127.0.0.1:56521`, so forwarding only the app would leave phone sign-in unable to reach Auth. Server requests are guarded to loopback/localhost, with synthetic task Auth/DB, no provider keys and preview-only delivery.

Read-only inspection found active interface `en0` / `192.168.1.11`. Docker already listens on wildcard host addresses for the task API 56521 and DB 56522; this task did not change those existing Docker bindings. Neither `mkcert`, `tailscale`, nor `iproxy` was found in PATH. No configured trusted phone HTTPS route was established by this assessment.

Booking, inspector and walk-in client code use `crypto.randomUUID`, which requires a secure context. An ordinary HTTP LAN URL is therefore insufficient for full workflow testing. See [MDN randomUUID](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID). Additional dev origins also require a narrowly scoped Next configuration; see [Next allowedDevOrigins](https://nextjs.org/docs/app/api-reference/config/next-config-js/allowedDevOrigins). Supabase redirect URLs would need separate consideration for link/redirect testing; basic password sign-in does not itself authorize changing them ([Supabase configuration](https://supabase.com/docs/guides/local-development/cli/config)).

Proposed bounded option, **not implemented**: a temporary HTTPS gateway at `192.168.1.11:56732`, restricted to the user's phone IP, serving the isolated app and a same-origin proxy for the task Auth/REST/Storage routes. The ignored preview's browser endpoint would require adapting to that gateway; server calls can remain on loopback. No SQL port, Studio, Auth-admin API, production credentials/data, provider endpoint or service-role key should be exposed by the gateway. Duration proposed: 30 minutes. The phone must already trust its TLS certificate, or the user must separately approve and perform any certificate-trust setup; certificate warnings must not be bypassed. Gateway behavior and role isolation must be verified before phone use.

Alternative: an explicitly approved private HTTPS tunnel to the isolated app/Auth gateway. That introduces a third-party transport and requires separate approval and access control; no tunnel was created. An HTTP static visual fixture could inspect layout but would not validate the actual authenticated workflows.

Minimal decisions needed before activation: approve the specific temporary phone-only network scope, supply the phone's Wi-Fi IP for the allowlist, and resolve trusted HTTPS. No activation is authorized by an unavailable approval relay. Upload testing has a separate blocker: Chrome extension file-URL access is disabled; enabling it expands local-file access and needs explicit approval.
